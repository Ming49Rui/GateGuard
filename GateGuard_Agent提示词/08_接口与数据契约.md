# GateGuard v3 接口与数据契约

版本 3.0，2026-11-23。本文是分发阶段的唯一接口设计基线，B 将其实现为 `src/gateguard/contracts/`、JSON Schema 和代码仓库接口文档。当前文件给出待实现约定，不代表已有可运行接口。A/B/C 为三名参赛成员，D/E/F 为辅助数据任务编号；各任务先按此开发。变更由 B 汇总影响，组长确认后升级契约版本，不允许各人另建不兼容模型。

## 1 数据分层与平台边界

- 电力输入是业务载荷，例如电压、电流、功率；模拟网关消费它，产生文件访问行为。
- 权限策略学习使用正常服务的系统行为，不直接拿电压值训练恶意分类器。当前方法为可解释规则归纳和验证收紧，没有预设神经网络。
- Windows：纯 Python 数据清洗、数据质检、离线策略学习、回放验证和图表；这些模块导入时不得要求 Linux BPF、cgroup、sudo 或挂载依赖。
- Ubuntu：模拟业务、真实采集、BPF 编译/加载、权限执行、隔离、快照及在线业务验证。后续在 openEuler 另做兼容验收。
- Windows 和 Linux 分别创建 Python 3.12 环境。BPF/加载器使用 C 与 Linux 工具链。源码通过 Git 统一，运行数据按校验和交换，不共用 `.venv`。

## 2 编码、标识和结果规范

所有记录 `schema_version` 为字符串 `3.0`。JSON/JSONL 为 UTF-8，无 BOM，JSONL 每行一个对象；规范导出 LF 换行。时间 `ts` 为 UTC ISO 8601，末尾 Z；`monotonic_ns` 是本次 Linux 启动会话的单调纳秒，只在相同 clock_id 内比较。

`run_id/scenario_id/family_id/service_id/instance_id` 为非空字符串；run_id 每次执行唯一，instance_id 每次目标启动唯一。Event 的 event_id 在 run 内唯一，推荐 `run_id:source:sequence`；实际 BPF 序号与用户态包裹关系须记录。每条测试动作有 operation_id，多个 hook 事件不能充当多次独立攻击；无法可靠关联时保留 null。

Linux `path` 保持 POSIX 语义，Windows 离线程序不能对其调用本机 realpath/resolve；归纳使用逻辑资源 `config/telemetry/reports/logs` 和相对路径。宿主机的本地数据包路径可使用 pathlib.Path，两类路径不能混用。PID、cgroup ID、inode 和绝对挂载路径只用于运行绑定，不直接固化为跨机器策略。

枚举如下，禁止各自另起同义名：

| 字段 | 值 |
|---|---|
| mode | learning / permissive / enforcing |
| label | normal / violation / boundary / recovery |
| operation | open / read / write / create / remove / rename / truncate / mmap_write / exec / connect |
| result | success / failed / unknown |
| verdict | allow / deny / would_deny / unsupported |
| evidence_kind | real / fixture / simulated_input |
| capability.status | supported / unsupported / unverified |
| policy.status | candidate / validated / approved / installed |
| check.status | passed / failed / not_checked |
| incident.state | detected / isolating / isolated / evidence_saved / stopping / stopped / recovering / verifying / restored / failed / rescue_required |
| snapshot.kind | baseline / periodic / incident |
| snapshot.trust_status | unverified / validated / approved / rejected |

open 的 O_WRONLY/O_RDWR 表示打开意图，不等于实际 write 成功；BPF LSM 允许也不等于后续 syscall 成功。没观测到返回值就写 unknown。缺失字段按 Schema 允许的 null 表达，不用 0 或空字符串伪装真实值。电力输入可以是 simulated_input，但主机访问证据仍需 real，不能一起标为“实测真实电力设备”。

## 3 核心记录

以下字段为接口设计所需字段。B 的实现应补齐类型、空值和长度校验，但不能擅自更改语义。

| 记录 | 必需内容 |
|---|---|
| TargetSpec | service_id、instance_id、Linux cgroup_path、cgroup_id、受信启动信息；PID 可为空 |
| RunContext | schema_version、run_id、scenario_id、family_id、seed、Linux output_dir、clock_id |
| Event | schema_version、event_id、run_id、service_id、instance_id、operation_id、ts、monotonic_ns、clock_id、pid、tgid、starttime、cgroup_id、comm、exe、syscall、path、flags、operation、result、errno、source、resource_id、policy_version、evidence_kind |
| ScenarioManifest | schema_version、scenario_id、family_id、service_id、label、seed、sandbox_id、operations、preconditions、expected_outcomes、recovery_trigger；operation_id 每项唯一 |
| Rule | rule_id、subject_id、resource（逻辑根、相对路径、匹配方式）、actions、effect、来源 run/event、support_count、validation、review_status |
| Profile | schema_version、profile_id、version、service_id、scope、rules、backend_requirements、validation_report、approval、status |
| Decision | schema_version、decision_id、event_id（可为空）、operation_id（可为空）、run_id、backend、requested_action、verdict、enforced、reason、rule_id、policy_version |
| Capabilities | schema_version、capability_id、OS/内核/BTF/LSM/工具链摘要、backend、逐动作状态、证据 run、限制、map ABI 版本 |
| Bindings | binding_id、instance_id、受保护挂载标识、资源对象映射、generation；由 Linux 当前环境生成 |
| PolicyBundle | schema_version、bundle_id、policy_version、capability_id、binding_id、backend、map_abi_version、编译规则、诊断、checksum |
| Incident | schema_version、incident_id、run_id、trigger_type、trigger_event_id（可为空）、service_id、instance_id、state、evidence_refs、recovery_point_id、error |
| Snapshot | schema_version、snapshot_id、run_id、service_id、kind、created_at、subvol_id、readonly、trust_status、manifest_hash、业务序号 |
| RecoveryReport | schema_version、incident_id、recovery_point_id、文件与元数据检查、保护重建检查、业务健康检查、rto_ms、rpo_ms、lost_legitimate_records、lost_legitimate_bytes、outcome、未检查项 |

Rule 的 actions 使用上述 operation 子集；本版不允许声称仅追加。effect 暂固定 allow，scope 内未授权动作由后端按契约处理。创建规则针对父目录和后端可表达条件；任意 glob/正则不能直接送入内核。A/B 必须在 G1 联调完成前发布 map ABI 的键值布局、上限、字节序和原子更新协议。

resource.match 固定 exact 或 directory；directory 是否递归、允许深度和动作必须明确且被后端支持。元数据中的 evidence_kind 不能取代 ScenarioManifest.label；两者分别表达来源真实性与场景真值。

电力输入由 D/C 固定为 UTF-8 CSV 或 JSONL，字段为 source_time（UTC 字符串）、device_id（字符串）、voltage_v/current_a/active_power_kw（数值或 null）、quality（valid/missing/invalid）、source_type（public_replay/synthetic）。单位转换有明确依据，不能把标幺值直接改名为伏特；缺失值处理保留来源与标记。业务启动时 C 校验该输入格式。

## 4 数据包与交付目录

Linux 每次采集写 `data/raw/<label>/<run_id>/`，由该次采集者持有；封包后不原地修改。D/E 执行采集，A 的 collector 只写指定 output_dir，C 管理目标与沙箱。不同 run 不共用可变 live 子卷。处理后的目录由 F 唯一维护。

```text
data/raw/<label>/<run_id>/
  events.jsonl          # 真实系统观测
  decisions.jsonl       # 后端裁决；未启用时为空文件并说明
  outcomes.jsonl        # 场景动作的实际结果，独立于 Guard
  manifest.json         # 本次场景与职责真值
  metadata.json         # OS、内核、工具、提交、seed、clock、能力等
  initial_files.json    # 内容、声明元数据与业务序号的初始真值
  final_files.json      # 场景执行后的文件真值
  checksums.sha256      # 对以上载荷计算；不包含自身
data/processed/<dataset_id>/
  dataset.json          # 原始 run 引用、hash、质量结论和排除原因
  splits.json           # train/validation/test 的 run_id 清单
  quality_report.json
  runs/<run_id>/        # 封包使用的原始 run 字节副本或可校验内容寻址载荷
  checksums.sha256
artifacts/policies/<experiment_id>/
  profile.json
  learn_config.json
  learning_report.json
  validation_report.json
  provenance.json       # 输入包 hash、代码版本、算法和随机种子
```

文件真值与 manifests 的内容 hash 用 SHA-256。校验和用于传输与一致性检查，不当作对 root 对手的数字签名。训练数据引用可解析为受控相对路径或 package_id，不携带仅某台 Windows 电脑有效的路径。元数据记录可为空或未测的 CPU/内存信息，不能编造。

F 导出的可分发 dataset 必须包含所引用 runs 的载荷，或一并交付其可验证内容寻址包；不能只复制 splits/processed 清单却缺原始事件。副本保持 raw 内容与 hash 不变。组长在 Windows 解包到新目录后，仅凭交付包即可完成 validate 和 learn。

train 只允许 normal；validation 主要用于正常可用性与参数选择。violation/boundary/recovery 和独立 normal test 用于最终测试，开发中调试的场景必须明确排除出冻结测试集。按 service/family/run 分组，不能随机拆同一 run 的事件造成泄漏。每个服务单独 profile。

## 5 Python 模块接口

以下是必须实现的签名约定，所有入参/返回模型由 B 提供。`Path` 是当前运行平台上的数据包路径，TargetSpec.cgroup_path 等保持 Linux 语义。

| 所有者 | 签名 | 执行位置与约束 |
|---|---|---|
| A | `Collector.start(target: TargetSpec, run: RunContext, emit: EventSink) -> CollectorHandle` | Linux；emit 不得阻塞内核裁决 |
| A | `Collector.stop(handle: CollectorHandle) -> CollectionSummary` | Linux；返回已写事件数、丢失计数、未完成关联和文件清单 |
| B | `Policy.learn(dataset_dir: Path, config: LearnConfig, output_dir: Path) -> LearnResult` | Windows/Linux 离线；验证来源和切分，只读训练部分 |
| B | `Policy.explain(profile: Profile, rule_id: str) -> RuleExplanation` | 纯 Python；带来源和必要性证据 |
| B | `Policy.validate_replay(profile: Profile, dataset_dir: Path, split: str) -> ValidationReport` | 离线回放；不能代替实际业务验证 |
| B | `Policy.judge(event: Event, profile: Profile) -> Decision` | 离线或兼容后端；不是 BPF LSM 的同步 RPC |
| B | `Policy.compile(profile: Profile, capabilities: Capabilities, bindings: Bindings) -> PolicyBundle` | Linux 集成入口；不支持语义时报错 |
| A | `Guard.capabilities() -> Capabilities` | Linux 真实探测；不能按版本号推断全部能力 |
| A | `Guard.install(bundle: PolicyBundle, expected_version: Optional[str]) -> InstallReceipt` | Linux；完整安装后原子切换，校验 binding generation 与 ABI |
| A | `Guard.set_mode(target: TargetSpec, mode: str) -> ModeReceipt` | Linux；记录实际状态，失败不静默降级 |
| A | `Cgroup.freeze(target: TargetSpec, timeout_s: float) -> IsolationStatus` | Linux；等待 frozen=1，拒绝根组和守护所在组 |
| A | `Cgroup.thaw(target: TargetSpec) -> IsolationStatus` | Linux；由 C 的事故流程调用 |
| A | `Cgroup.terminate(target: TargetSpec, timeout_s: float) -> TerminationStatus` | Linux；仅登记目标，使用实测 kill 路径并等待 populated=0，超时返回失败 |
| C | `ScenarioRunner.run(manifest: ScenarioManifest, run: RunContext) -> ScenarioResult` | Linux；启动登记目标，调用 A，执行白名单场景驱动并封包 |
| C | `Gateway.health(target: TargetSpec) -> HealthReport` | Linux；含实际采样/查询，不只进程存活 |
| C | `Response.isolate(incident: Incident) -> Incident` | Linux；固定事故并持久化状态 |
| C | `Response.recover(incident_id: str, point_id: str, request_id: str) -> RecoveryJob` | Linux；request_id 幂等，返回可查询任务 |
| C | `Response.status(job_id: str) -> RecoveryStatus` | Linux；终态包含 RecoveryReport 或结构化失败 |
| B | `Store.append_event/append_decision/append_incident/append_snapshot/append_recovery_report(record) -> str` | Linux 单写入口；返回记录 ID |
| B | `Store.query_events/query_incidents/get_profile(...)` | Linux 只读查询；分页/筛选参数写入实现接口文档 |
| B | `Dataset.validate(dataset_dir: Path) -> DatasetValidationReport` | 纯 Python 结构/hash/引用校验；F 增加业务数据质量分析 |

LearnConfig 至少包含 method（manual/exact/grouped）、seed、训练与验证划分 ID、规则收紧与归纳参数、允许的业务分区、后端目标语义。manual 方法还要求提供人工职责规则文件及来源 hash，不从最终测试结果倒推人工基线；exact/grouped 从 normal train 生成。LearnResult 返回 profile_path、报告路径、输入 hashes 和状态；组长决定参数与最终选择，B 不替组长冻结最终实验结论。

## 6 C 统一实现的命令行门面

以下是开发目标，仓库当前可能尚未提供这些命令。C 负责 `gateguard.cli`，内部调用上述所有者实现；DEF 不各写一套特权采集/恢复入口。

```text
python -m gateguard.cli preflight --out <capabilities.json>
python -m gateguard.cli scenario run --manifest <manifest.json> --out <run_dir>
python -m gateguard.cli dataset validate --dataset <dataset_dir>
python -m gateguard.cli policy learn --dataset <dataset_dir> --config <learn_config.json> --out <artifact_dir>
python -m gateguard.cli policy explain --profile <profile.json> --rule <rule_id>
python -m gateguard.cli policy validate --profile <profile.json> --dataset <dataset_dir> --split validation
python -m gateguard.cli policy install --profile <profile.json> --target <target_id>
python -m gateguard.cli mode set --target <target_id> --mode enforcing
python -m gateguard.cli incident recover --incident <id> --point <id> --request <id>
python -m gateguard.cli incident status --job <id>
```

Windows 支持 dataset validate、policy learn/explain/validate；preflight、scenario、install、mode、incident 为 Linux-only，其他平台返回 PLATFORM_UNSUPPORTED。CLI 在 Windows 可正常显示帮助和执行离线功能，不因导入 Linux 模块失败。

## 7 传输、异常与审批

离线交换采用版本化 JSON/JSONL 文件包；不为一次训练引入网络服务。Windows 与 VM 通过 SSH/SFTP 或显式复制数据包交换，接收后核对 checksum。CLI 调守护进程使用鉴权 Unix socket；BPF 规则经 map 与 link 管理，不经 HTTP 请求逐次裁决。

统一异常结构 `code/message/retryable/context`，context 含 request/run/incident ID，不能含密码或 token。code 包括 SCHEMA_UNSUPPORTED、DATA_INVALID、PLATFORM_UNSUPPORTED、CAPABILITY_UNSUPPORTED、PRECONDITION_FAILED、POLICY_CONFLICT、TIMEOUT、RECOVERY_FAILED、INTERNAL_ERROR。unsupported 与未验证不得转成 allow。

CLI 退出码约定：0 成功；2 参数或数据错误；3 平台/后端不支持；4 前置条件失败或版本冲突；5 超时/运行失败。执行失败不能只写日志仍返回 0。恢复异步接受不代表恢复成功，最终 outcome 由 status 获取。

ScenarioRunner 执行违规动作时须让动作归属声明的目标服务身份/cgroup，记录真实 TargetSpec；以 root 或另一个未绑定主体执行而产生的拒绝不计目标服务防护成功。C 负责启动受控 helper，E 仅提供驱动和动作参数。

恢复后 C 先预建新的 instance_id 与服务 cgroup，A/B 为当前卷创建新 Bindings 并安装保护，再启动进程，补充 PID 等信息。旧实例/旧绑定失效；不能先启动未受保护业务再补策略。命令 install/mode/recover 通过普通用户 CLI 连接特权助手，权限不足返回错误，不自动提升整个 IDE。

策略先 candidate，离线正常回放通过后 validated，组长审核后 approved，再编译安装为 installed；安装后在隔离测试目标上进行真实 Linux 正常业务验证，结果回写 validation_report。只有实际业务验证通过的安装版本才能验收为最终版本，避免“尚未安装却要求先完成执行验证”的循环。验证失败保持失败记录并切回上一有效版本或停服，不自动放宽规则。permissive 的 would-deny 不计实际阻断；新增白名单不是自动接受异常。Web 修改操作采用鉴权写请求，特权助手只接受登记资源 ID 和固定动作，校验 socket 对端；C 的 Web 路由说明经 B 合入其维护的 docs/interfaces.md，不另改核心模型。

执行模式对登记主体在受保护 scope 内、后端声明覆盖的动作采用默认拒绝：没有匹配 allow 即 deny。scope 外仍受系统 DAC/其他 LSM 约束，不宣称已被 GateGuard 覆盖。learning/permissive 不能绕过其他安全机制。不支持的策略在编译/安装阶段报错，不转换成隐式 allow。

冻结后的目标不能继续执行普通退出处理。事故流程默认在留证后通过已验证的 cgroup.kill 或受控 SIGKILL 终止目标，等待 cgroup.events 的 populated=0，并确认其他进程/监听不再引用挂载点。若选择优雅退出，须先建立并验证独立的有效隔离，再受控解冻并设置超时；不能只发 SIGTERM 后一直等待，也不能先无保护解冻。A 实现 kill/wait 原语，C 编排并记录，能力以目标内核实测为准。[Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)。

## 8 五个联调关口

| 关口 | 进入下一阶段的条件 |
|---|---|
| G0 契约与环境 | B 发布共享模型与 fixtures；C 工程入口；A Ubuntu 探测与最小 BPF 结果；DEF 能校验 fixture |
| G1 小批真实数据 | C 网关正常业务 + A 真实采集；DEF 输出完整 run 包，F 质检通过，组长/B 确认可用于学习 |
| G2 策略学习与执行 | 组长在 Windows 运行 B 的程序；回传高层策略；A/B 编译安装并验证读允许写拒绝，C 跑正常业务 |
| G3 独立恢复 | E 先确认合成数据损坏；C 停服恢复、重建保护并健康检查；F 保留数据损失真值 |
| G4 冻结评测与交付 | 冻结测试清单，组长组织对照/消融；Ubuntu 结果可复现，openEuler 迁移单列；代码、文档、视频一致 |

大家可在 G0 并行开发各自模块；G1 通过前不批量采集，G2 通过前不宣称精细控制完成。接口差异由 B 修复并记录版本；内核缺口由 A 报告，恢复缺口由 C 报告，数据问题由 DEF 补证，最终取舍由组长负责。
