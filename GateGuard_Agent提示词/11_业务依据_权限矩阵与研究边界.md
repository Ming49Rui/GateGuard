# GateGuard 业务依据、权限矩阵与研究边界

文档版本 3.1，2026-11-24；数据结构以 [08 契约](08_接口与数据契约.md) 为准。本文件是 ABC/DEF 的共同需求基线，描述待实现原型，不代表现场部署或实验成果。

## 1 主要解决什么问题

GateGuard 是面向电力边缘服务的 Linux 文件权限策略生成、访问控制与可验证恢复工具，参加操作系统应用开发赛道的系统工具方向。

| 具体问题 | 拟解决方式 | 验证依据 |
|---|---|---|
| 服务文件权限配置粗放，人工细化和维护困难 | 将业务职责与正常访问证据结合，生成带来源的候选规则 | 人工职责、精确汇总、简单目录归纳与自研方法的对照 |
| 精确白名单覆盖不足，目录放权可能过宽，收紧代价不清楚 | 对正常生命周期、新日期和职责外操作分别验证，报告授权扩大与业务失败 | 正常任务完成率、额外授权、规则数；离线与 Linux 实测分开 |
| 权限内数据也可能损坏，恢复后状态和合法损失难核验 | 留证、停服恢复、重建保护，再检查文件、业务和损失 | 损坏前/后/恢复后事实，恢复点、保护检查、业务序号及损失报告 |

不预设上述指标一定优于基线，不把规则更少等同于更安全，不以“电力＋AI＋eBPF”的名称组合充当贡献。

## 2 操作系统主线与边界

核心链路为进程身份与文件操作采集 → 用户态策略生成/解释/编译 → 已验证 BPF LSM 钩子的同步访问检查 → cgroup 进程控制 → Btrfs 停服恢复及保护重绑定。Windows 仅承担离线处理；运行与验收在 Linux VM。openEuler 能力另行验证。

| 范围 | 本原型约定 |
|---|---|
| 主体 | 受信启动配置登记的普通服务实例及其受控 cgroup；不信任请求中自报的角色或 device_id |
| 客体 | 显式登记的文件/目录和保护挂载；编译时绑定当前 Linux 对象 |
| 动作 | 08 的 operation；只承诺后端已验证支持的子集 |
| 不纳入核心 | 电压预测、电网故障诊断、遥控命令授权、数据库行/列鉴权、应用登录用户间权限判定 |
| 安全边界 | 不抵御 root/内核失陷；允许写入不代表内容正确；同 cgroup 子进程不自动获得不同权限 |

软件可以在用户态开发；技术深度通过真实系统行为、内核拒绝、对象生命周期、故障处理和可复现实验体现。

## 4 本项目的模拟业务约定

C 实现一套小型采集、报表、维护业务，D 提供电力记录和正常负载。为研究服务级文件权限，本原型主动采用可分离的文件分区；这是团队模拟约定，不是对 Fledge 或真实电站架构的复刻。

首轮每个 run 使用一个专用 live 挂载点；主体固定为 `collector`、`reporter`、`maintainer` 三个稳定 service_id。启动实例另有 instance_id/cgroup。资源 ID 固定为 `config`、`telemetry`、`reports`、`logs`，根相对路径同名。设备 ID 只作业务属性，本版不强制每设备一个文件/服务；确需设备隔离时须显式新增可区分主体与资源，不能靠 CSV 中 device_id 获得权限。

推荐数据布局：`config/device.json`、`telemetry/<UTC-date>.jsonl`、`reports/<UTC-date>.json`、`logs/<service_id>/`。日期命名是负载变化；不是可任意授权所有数字名称的理由。实际文件格式和必要原子更新步骤由 C 与 B 在 G0 登记，D/E 不自行改布局。

### 4.1 核心职责矩阵

下表是初始模拟规格。B/C 在正式采集前确认并版本化；动作展开为 08 的 BusinessSpec，不能直接把自然语言表作为已实现内核规则。

| 服务主体 | config | telemetry | reports | logs |
|---|---|---|---|---|
| collector | 读取指定配置文件；禁止修改 | 读取/写入采集文件，按需要创建新日期文件；删除、重命名、截断须单独论证 | 禁止访问 | 仅本服务日志的已登记写入、创建和轮转步骤 |
| reporter | 默认不访问；若业务确需读取指定配置则先修订规格 | 读取指定数据；禁止修改 | 按报表流程读取、创建、写入；替换旧报表涉及的 rename 等须单列 | 仅本服务日志的已登记操作 |
| maintainer | 指定配置的读取、创建、写入；原子替换涉及的 rename/父目录权限须明确 | 禁止访问 | 禁止访问 | 仅本服务日志的已登记操作 |

矩阵范围外不宣称已保护。精确的 open/read/write/create/remove/rename/truncate 等动作应按真实程序展开，不能把“保存”直接当作一个 syscall。对 rename 同时检查源/目标，对 create 登记父目录；日志轮转不要扩大到其他服务日志。配置重载由 collector 读取新配置，配置写入由独立 maintainer 完成。

三种职责必须映射到可区分的受控进程/cgroup。应用界面里的角色名称、同一进程内的函数名称不能替代内核主体。实验中可在相同普通 UID 下用不同受控 cgroup 验证服务策略的增量，但目标不能自行迁移 cgroup。先检查无 Guard 时 DAC/其他 LSM 是否允许目标动作。

业务阶段 startup/sampling/query/report/rotation/reload/restart/maintenance 用于覆盖分析与解释；若没有可信阶段切换机制，本版不按自报阶段动态放权。维护始终使用独立主体。

### 4.2 越权、误拒与内容错误

- **业务越权**：独立 BusinessSpec 对登记主体、对象、动作给出 deny，实际尝试超出职责；是否被挡住另看真实裁决与结果。
- **策略误拒**：业务规格允许的正常需求被 Guard 拒绝，例如新日期文件创建没有被覆盖。
- **内容错误**：主体有权写 telemetry，却写错内容。文件权限不判数据值真假，单列 recovery 场景。
- **未定情况**：业务规格缺依据、资源解析失败或条件不明确，标 unspecified/unknown，不凑成阻断成功率。

一次 deny 不等于恶意，训练未见不等于违规，syscall 失败也可能来自 DAC、路径不存在等原因。

## 5 给 B 的输入与留给评测的真值

BusinessSpec 是团队审核的完整模拟授权规格；LearningConstraints 是面向学习的粗粒度约束投影；EvaluationInventory 是独立的有限资源—动作评测清单。字段、文件、hash 引用统一见 08。

- 学习输入：已准入的 normal train 观测、资源目录和已声明的粗粒度职责边界。低频、失败、未知事实保留，但不能自动转成授权。
- 评测依据：先于最终实验确认的业务规格和评测清单；不从 Guard 输出生成正确答案，不向学习器提供冻结 test 的预期与结果。
- 人工职责策略可按 BusinessSpec 编写并提前固定，披露其人工知识输入；不能把完整精确规则交给算法后宣称自动发现。
- 已知硬约束若完全禁止某类访问，该类额外授权应为零；单独报告约束符合性。归纳代价在尚有选择空间的范围内度量，不用“违反已知约束更少”包装成算法研究成果。
- 最终正常完成率和阻断能力需要 Linux 实测；离线匹配只说明所观察记录的覆盖情况。

## 6 拟验证贡献与待讨论事项

研究问题：在业务职责与后端能力约束下，如何从有限正常文件访问生成兼顾业务可用性、较小额外授权和规则复杂度的策略？

| 拟验证贡献 | 对照/证据 |
|---|---|
| 职责约束与受控归纳 | 对照精确汇总、简单目录归纳；比较范围、规则数和未见正常需求覆盖 |
| 规则选择与验证收紧 | 保持候选和数据条件可比，检验关闭选择/收紧的消融；报告失败与代价 |
| 可追溯解释 | 来源证据完整率、固定问题的解释正确率；人工效率须另做审核实验 |
| 编译执行一致性与恢复闭环 | 后端动作矩阵、实际拒绝、当前资源重绑定、文件/业务/合法损失证据 |

算法评分函数、风险权重、候选搜索策略、阈值与最终参数留待 B 的算法讨论；本轮不指定唯一优化算法，不承诺全局最小权限或优于所有基线。eBPF/LSM/cgroup/Btrfs 是成熟构件，团队贡献体现在规则方法、执行语义与证据验证。
